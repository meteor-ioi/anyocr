# 复杂系统与深度学习工程架构守则 (Systems & DL Architecture Guardrails)

本规则适用于所有涉及复杂底层系统、深度学习推理引擎、格式解析与编译器/AST 等非琐碎工程模块的设计与开发。

---

## 一、 重型资源与推理引擎生命周期
1. **显式生命周期控制**：涉及大文件加载、图优化、硬件会话绑定的重型引擎（如 ONNX Runtime、Torch、LLM Session），严禁在核心层设计纯无状态冷启动函数；
2. **所有权显式持有**：必须暴露显式结构体（如 `Engine::new(config)`），由调用方显式持有和复用会话；
3. **双层 API 架构**：开箱即用的顶层函数只作为便捷封装，内部基于惰性单例（如 `OnceLock`）缓存实例，禁止硬编码死锁阻碍多实例隔离与测试。

## 二、 版式感知与视觉文档数据建模
1. **以页为基元解耦**：处理天然多页版式（PDF/OFD/多图），核心数据结构必须以“页”为单位解耦（`PageResult`），独立持有物理尺寸、AST 块和坐标；
2. **严禁全篇平铺坐标**：杜绝跨页共享同一套二维坐标系，防止不同页面相同物理坐标产生空间碰撞，破坏原图高亮、卷帘联动与脱敏审计。

## 三、 技术选型能力边界与显式失败
1. **清晰划分语法解析与光栅化渲染**：严禁混淆“语法解析器”（如 `lopdf`）与“光栅化渲染器”（如 `pdfium`）；
2. **严禁静默失败**：遇到超出库当前能力边界的场景（如纯矢量无字“假扫描件”），必须返回显式强类型错误（如 `AnyOcrError::PdfError`），绝不允许静默吞掉或虚假返回空结果；
3. **依赖隔离**：高成本系统依赖（动态链接 C 库等）必须以可选 Feature 隔离，维护基础库的便携性。

## 四、 Rust 库工程与 Feature Gating 纪律
1. **类型系统与特性对齐**：当 API 公开类型枚举包含可选特性的变体时，未开启对应 Feature 必须返回显式错误（如 `UnsupportedFormat`），绝不允许出现编译通过但运行时 panic；
2. **格式依赖显式开启**：声明支持的文件格式必须在依赖配置中显式开启相应的解码特性（如 `image` 的 `tiff`）。

## 五、 敏捷落地闭环节奏
1. **垂直单调递增**：依赖链路必须保持单调递增，最小输入（解码）+ 最小处理（Baseline 逐行推理）+ 冒烟测试闭环优先于任何高级算法；
2. **性能优化后置**：分桶批处理（Bucket Batching）等吞吐性能优化必须在 Baseline 跑通后再以独立 PR 叠加，杜绝依赖悬空。

## 六、 图像输入自适应上限与几何坐标保真
1. **尺寸上限钳制**：面向通用 OCR 管道，必须设置最长边上限（默认推荐 2560px，严格对齐 32 卷积步长与 8pt 小字采样），杜绝超大扫描图直接引发的 $O(N^2)$ 内存与重采样开销；
2. **坐标物理还原铁律**：内部降采样推理的所有包围盒（`bbox`、`TextBoxItem.coords`），必须在 AST 序列化前通过尺度逆变换还原为用户原图物理视窗坐标，保证几何空间绝对一致性。

## 七、 小语种与多语言扩展解耦
1. **感知与语言解耦**：文本行检测（DBNet）与表格拓扑预测（SLANet）必须保持语言无关（Language-Agnostic）；
2. **零侵入即插即用**：小语种扩展严禁修改核心推理链路，统一通过 `ModelProfile::Custom` 在识别器与字典维度进行挂载与热插拔。
