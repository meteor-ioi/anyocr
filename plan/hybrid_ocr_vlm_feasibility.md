# 混合级联 OCR (传统轻量 OCR + 端侧小 VLM 局部精修) 可行性分析报告

## 1. 背景与核心动机

在端侧文档转换（如 `anydoc`）的实际生产环境中，面临着严苛的硬件与体验约束：
* **目标运行环境**：普通消费级笔记本（4 核 CPU、16GB RAM、无独立显卡/纯集成核显）。
* **传统 OCR 流水线痛点**（如 PP-OCRv6）：
  - 运算速度极快（CPU 单页仅需 300~500ms），内存开销极小。
  - 但基于 CTC 的字符识别错误率高（数字 `77` 识别为 `zZ`、英文丢失空格、符号识别不准）。
* **端侧小 VLM 痛点**（如 Qwen3.5-0.8B + mmproj）：
  - 端到端 Markdown 排版与语义纠错能力出众。
  - 但全图 Token 爆炸（整页高分辨率切分为 2000~4000 个视觉 Token），在 4 核纯 CPU 下遭遇严重的 Prefill 算力瓶颈与自回归 Decode 带宽瓶颈，导致单页耗时高达 30~50 秒，无法满足多页批处理需求。

**核心洞察**：
通过“**传统 OCR 全局粗扫 + 低置信度区域局部切片 VLM 精修**”的混合级联架构（Cascaded Fallback），将 VLM 的输入从“整页 A4”缩小至“几十像素的文字补丁”，在纯 CPU 上兼顾亚秒级速度与大模型级的高精度。

## 2. 架构设计与数据流

```text
[ 输入文档图像 (Image / PDF Page) ]
                │
                ▼
      [ PP-OCR 快速粗扫 ] (纯 CPU 耗时 ~300ms)
                │
                ├───────────────────────────────────────┐
                ▼                                       ▼
    [ 提取文本块与置信度列表 ]                  [ 保留原始图像与坐标 ]
                │
                ▼
   [ 筛选低置信度区块 (Score < 0.6) ]
                │
         (有低置信度区块?)
          ├── 否 ──> [ 直接输出识别结果 ] (耗时 < 0.5s)
          └── 是 ──> [ 空间聚类与熔断保护 ]
                         │  (相邻框合并为一个 BBox，单页上限 5 个)
                         ▼
                   [ 裁剪带上下文的局部切片 (Padding 1.5x) ]
                         │
                         ▼
                   [ Qwen3.5-0.8B VLM 局部二次识别 ] (每个切片 ~1.0s)
                         │
                         ▼
                   [ 原位替换低置信度文本内容 ]
                         │
                         ▼
                   [ 输出高精度结构化文本 ]
```

## 3. 为什么该方案能成倍提速？（算力与数学推导）

在 4 核 CPU 上，VLM 推理的耗时由两部分构成：
$$T_{\text{total}} = T_{\text{prefill}} (\text{视觉编码 + 注意力上下文}) + T_{\text{decode}} (\text{自回归逐字生成})$$

| 指标 | 全页 VLM 识别方案 | 混合级联局部精修方案 (单切片) | 优化幅度 |
| :--- | :--- | :--- | :--- |
| **输入分辨率** | 2000 × 3000 (整页 A4) | 300 × 100 (局部文字补丁) | 像素量下降 **99.5%** |
| **视觉 Token 数** | 2048 ~ 4096 个 | 36 ~ 64 个 | Token 量下降 **98%** |
| **Prefill 首字延迟** | 12 ~ 20 秒 (CPU 矩阵乘法瓶颈) | 0.2 ~ 0.4 秒 | 提速 **30~50 倍** |
| **生成字数 (Decode)**| 500 ~ 1000 字符 (全文) | 3 ~ 15 字符 (仅当前词/句) | 解码步数下降 **98%** |
| **总推断耗时** | **30 ~ 50 秒** | **0.8 ~ 1.5 秒** | **极速响应** |

**实际综合收益预估**：
在一份普通质量的扫描文档中，低置信度区域通常为 1~3 处。
$$\text{总耗时} = 0.3\text{s (粗扫)} + 2 \times 1.2\text{s (精修)} \approx \mathbf{2.7 \text{秒}}$$
相比纯 VLM 方案，单页耗时从近 1 分钟压缩到 3 秒以内，完全处于桌面交互工具的可用阈值之内。

## 4. 关键技术点与工程避坑指南

### 4.1 空间聚类（防止雪崩效应）
* **风险**：若扫描件整体有轻度水印或噪点，可能产生 50+ 个低置信度文本框。如果串行调用 50 次 VLM，耗时将恶化至 1 分钟以上。
* **工程解法**：
  1. **空间合并（Bounding Box Merging）**：在水平方向上距离小于阈值（如 $1.5 \times$ 行高）的框，直接合并为一个外接矩形，一次性送入 VLM。
  2. **最大重试熔断（Circuit Breaker）**：单页最多仅允许修剪置信度最低的 Top-N（建议 $N=5$）个区块。超过上限直接降级为人工标黄或仅保留原识别内容。

### 4.2 包含上下文的裁剪（Context Padding）
* **风险**：若仅严密贴合文字边缘裁剪（如仅裁切 `77` 两个数字），VLM 在缺乏周边单词语法线索的极小分辨率下容易误判或拒绝回答。
* **工程解法**：
  - 裁剪时四周施加 Margin/Padding（建议横向扩展 20px，纵向扩展 0.5 倍行高）。
  - 给 VLM 明确且严谨的系统指令：
    > `请识别图像中心主体文字，参考周边环境排除歧义，仅输出识别结果，禁止解释和推理。`

### 4.3 显存/内存管理与推理配置
* **常驻守护模式**：`Qwen3.5-0.8B-Q4_K_M.gguf` (~532MB) 与 `mmproj-BF16.gguf` (~207MB) 必须以常驻常开的 Server 进程挂载（常驻内存占用 < 800MB），杜绝每次识别重新读取 GGUF 文件的 IO 损耗。
* **严控解码循环**：
  - 必须添加启动参数 `--reasoning off`（关闭 Qwen 思维链，严禁其展开长篇思考）。
  - 推理参数固定：`temperature = 0.0`, `top_p = 0.1`, `max_tokens = 32`。

## 5. 方案的能力边界（解决什么 vs 解决不了什么）

### ✅ 完美覆盖的场景
1. **形近字符与数字混淆**：有效区分 `77` / `zZ`、`0` / `O`、`1` / `l` / `I`。
2. **专业术语与专有名词**：利用小大模型的语言常识纠正词典外的生僻词。
3. **模糊或微倾斜字迹**：利用 VLM 强大的语义先验补全缺损笔画。

### ❌ 无法单独解决的问题（需辅助手段）
1. **全局版面分析与表格骨架错位**：
   - 局部切片精修仅针对“字符识别”，不能修正文本框之间的行列逻辑对齐关系。
   - 表格重构仍需依赖规则后处理，或提取文本后送给纯文本极小 LLM 进行轻量级重排。

## 6. anydoc 项目落地实施路线建议

* **第一阶段：置信度探针与日志打点**
  - 在 `anydoc` 的 OCR 识别通道中，暴露每个文本框的 `confidence` 置信度指标。
  - 统计实际业务文档中 low-confidence (< 0.6) 框的出现频次与分布密度。
* **第二阶段：局部裁剪与聚类工具库**
  - 实现基于坐标距离的 BBox 合并逻辑与带 Padding 的图像局部切片工具。
* **第三阶段：接入本地轻量 VLM Client**
  - 集成基于 HTTP/IPC 的局部图像送审客户端，对接本地常驻的 `llama-server`。
  - 验证原位替换（In-place Text Replacement）后的整篇 Markdown 输出效果。
* **第四阶段：熔断策略与降级开关**
  - 增加配置项（允许用户一键关闭二级精修以追求极限纯 OCR 速度）。
